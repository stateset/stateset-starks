# Binding the proved amount to the event payload — design

**Status:** implemented on the `ves-stark` side (`ves_stark_primitives::payload_v2`,
verifier hook, all bindings pass `restHash` through; tests in
`tests/payload_v2_binding_test.rs`). Awaiting the sequencer, which must emit
`payload_kind = 2` events per the contract below; until then no live event
exercises the path.

## The gap

Today a compliance proof attests, for public inputs `P` and commitment `C`:

> there exists `(amount, salt)` with `amount <= L` and `C = Rescue(amount ‖ salt)`.

It does **not** attest that `amount` is the amount on the event whose hashes sit
in `P`. `SOUNDNESS.md` states this plainly. The current mitigation is the
`PayloadAmountBinding` artifact — a *protocol-level* attestation checked by the
verifier outside the circuit — which means the binding is only as trustworthy as
whoever signs that artifact. A prover who controls the witness can commit to
any compliant number and produce a valid proof for a non-compliant order.

This is the one property whose absence changes what a verifier may conclude.
Everything else in the hardening backlog is robustness.

## Two ways to close it

### A. Prove the amount is a substring of the hashed payload

Hash the full payload in-circuit and constrain that the canonical serialization
of `amount` appears at the right offset. Rejected: the payload is SHA-256'd by
the sequencer (`payload_plain_hash`), so this means a SHA-256 circuit — tens of
thousands of constraints per block, a different hash from everything else in
the system, and a proving-time regression of one to two orders of magnitude.

### B. Put the witness commitment inside the payload hash — recommended

**Revision note.** An earlier draft of this option proposed an *unsalted* leaf
`Rescue(amount ‖ 0)` as a new public input. That is a flaw: STARK public inputs
are visible to every verifier, and an unsalted commitment over a low-entropy
amount is brute-forceable — the exact hiding failure the salted witness
commitment `C` exists to prevent. Salting the leaf fixes it, and once it is
salted it has the same shape as `C`. So the leaf *is* `C`, and the circuit does
not change.

Restructure the payload commitment so the salted witness commitment the circuit
already binds is a component of what the sequencer hashes:

```
payload_plain_hash  =  SHA-256( domain ‖ C ‖ rest_hash )
C                   =  Rescue( amount_lo, amount_hi, salt0..salt3, 0, 0 )   // existing
rest_hash           =  SHA-256( everything in the payload except amount and salt )
```

The salt lives in the payload (the sequencer already sees the amount; it now
also carries the 128-bit salt, generated by whoever authors the event). The
prover uses the same salt for `C`; it does today. `rest_hash` is published in the
canonical public inputs as `restHash` so the verifier can recompute
`payload_plain_hash` — a single native SHA-256 over 68 bytes.

**Circuit changes: none.** The AIR already boundary-asserts
`RESCUE_STATE[0..4] == C` at the output row and constrains `C` from the same
`AMOUNT[0..2]` limbs the comparison gadget reads. Binding `C` into
`payload_plain_hash` makes that existing assertion mean "the amount on the
event", with no new columns, constraints, or proving cost. `NUM_CONSTRAINTS` and
`NUM_BOUNDARY_ASSERTIONS` stay 157 / 76.

### What the statement becomes

> there exists `(amount, salt)` such that `amount <= L` and
> `C = Rescue(amount ‖ salt)`, where `C` is a component of `payload_plain_hash`.

`amount` is now the amount on the event, up to Rescue collision resistance —
the same assumption every Merkle path in the batch AIR already rests on. Hiding
is unchanged: `C` was already public; it is salted; `rest_hash` reveals nothing
about the amount.

### Where trust moves

The binding is only as good as the sequencer computing `C` from the real amount
when it forms `payload_plain_hash`. That is the same party, and the same step,
that every consumer already trusts to produce `payload_plain_hash` at all — so
this adds no new trusted component, and it removes one: the `PayloadAmountBinding`
artifact and its signer become unnecessary.

## Verifier changes (`ves-stark-verifier`)

For `payload_kind == 2`:

1. Parse `C` from the proof (already done) and `restHash` from the public inputs.
2. Recompute `SHA-256(domain ‖ C_bytes ‖ rest_hash)`; require equality with
   `payload_plain_hash`. `C_bytes` is the four limbs as 8-byte **big-endian** words, 32 bytes — the
   existing `witness_commitment_u64_to_hex` convention — pinned by a KAT.
3. Everything else unchanged.

`verify_*_with_amount_binding` becomes a no-op wrapper for kind 2 that logs a
deprecation; `ComplianceVerification::amount_binding` gains a kind-2 path that
needs no artifact.

## Sequencer contract (`stateset-sequencer`)

- Accept a 128-bit `salt` in the event payload (authored by the event producer,
  random). Compute `C` with `ves_stark_primitives::rescue::amount_witness_commitment_salted`
  and publish the exact vector in `docs/rescue_constants.json`.
- Emit `payload_plain_hash` as above with `domain = b"STATESET_VES_PAYLOAD_V2"`.
- Carry `restHash` (hex, 64 chars) in the canonical public inputs;
  `payload_kind = 2`.

## Migration

1. Sequencer ships V2 hashing behind `payload_kind = 2`; V1 unchanged.
2. `ves-stark` 0.6.0 adds the verifier path. **No prover or AIR change**, so
   proofs are not invalidated: a 0.5.0 proof over a V2 event verifies under the
   stronger statement as soon as the verifier upgrades.
3. Once no V1 events remain in any active batch window, drop the artifact code.

## Cost

Zero proving-time impact. One extra native SHA-256 per verification.

## Batch proofs — needs an AIR change (corrected)

An earlier version of this section claimed batch V2 was "feasible without a
circuit change" by having `BatchVerifier` recompute
`SHA-256(domain ‖ witnessCommitment ‖ restHash)` per event against each event's
bound `witnessCommitment`. **That is unsound.** The constraint chain does not
support it, verified by reading the batch AIR:

- Each event's leaf carries two independent values: `amount_commitment`
  (`= rescue_hash(amount_limbs)`, the in-circuit commitment the compliance
  constraints prove is over a policy-compliant amount) and `public_inputs_hash`
  (`compute_bound_hash`, a **native SHA-256** — opaque to the circuit — that
  contains the *public* `witnessCommitment` field).
- Nothing in-circuit proves `amount_commitment` equals the `witnessCommitment`
  inside `public_inputs_hash`. Only a prover-side check
  (`prover/witness.rs`, "witness_commitment != expected") enforces it, and a
  malicious prover skips prover-side checks.
- The per-event `amount_commitment` accumulator (`batch_trace.rs`) is **not** a
  public input; `BatchPublicInputs` exposes only `public_inputs_accumulator`,
  which folds the native bound-hash — i.e. the free public field.

So a malicious prover could prove compliance for a compliant in-circuit amount
A while setting the public `witnessCommitment` (and thus the V2 payload binding)
to the real, non-compliant amount B. The batch verifier re-hashing the public
field would "bind" B and accept — exactly the forgery V2 is meant to stop.

Why the **non-batch** verifier is sound by contrast: `verify_compliance_proof`
takes the `witnessCommitment` and the AIR boundary-asserts the trace commitment
equals it, so the value V2 re-hashes is provably the compliant amount's
commitment. Batch has no equivalent per-event boundary assertion.

**What batch V2 actually requires:** an AIR change — expose the in-circuit
`amount_commitment` accumulator as a public input and constrain it, then have
the verifier recompute it from a caller-supplied list of per-event commitments
(authenticating the real in-circuit values) and re-hash *those* for V2. This
invalidates existing batch proofs, so it is a 0.7.0-class change, not a verifier
patch. Until then, `SOUNDNESS.md` states that batched V2 events carry only the
V1-equivalent guarantee.

## Tests that must exist before this ships

- `test_payload_hash_mismatch_rejected_v2`: valid proof, `restHash` swapped →
  rejected, because `SHA-256(domain ‖ C ‖ restHash') != payload_plain_hash`.
- `test_commitment_not_in_payload_rejected`: valid proof over `C`, public inputs
  whose `payload_plain_hash` was formed from a different `C'` → rejected.
- KAT for `C_bytes` serialization and the V2 hash, generated by the independent
  Python implementation.
- `docs_consistency_test`: constraint counts unchanged (157 / 76) — this design
  must not silently grow the AIR.
